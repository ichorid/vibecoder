# VIBE CODER — пофазовый план реализации с TDD

Статус: план, задачи ещё не выполнены. В репозитории есть дизайн и архитектура; каркас приложения, линтеры и тесты предстоит создать. Этот документ не подтверждает работоспособность игры.

Основание: [архитектура](architecture.md), [игровой дизайн](initial_design.md), [правила использования визуальных референсов](design_references/README.md). Согласованный стек: **TypeScript + Vite + Svelte 5 + PixiJS 8**, чистая TS-симуляция, LocalStorage. Выбор Svelte заменяет исходную рекомендацию React в первоначальном дизайне. Содержание и ограничения игрового опыта сохраняются.

## 1. Как выполнять план

Один агент выполняет **одну задачу с ID**, например `P04.2`, за проход. Читает этот документ, соответствующий файл фазы, указанные разделы архитектуры и затрагиваемый код. После каждого проверенного изменения оставляет короткую запись. Переходить к следующей фазе можно после её выходного контроля.

Порядок строго последовательный. План не требует параллельных агентов. Если задача не помещается в один понятный патч, разделить её на меньшие циклы внутри того же ID; не захватывать следующую подсистему. Фаза — несколько завершённых задач, а не один огромный коммит.

## 2. Обязательный цикл TDD

Для каждого поведения:

1. **RED:** написать один небольшой тест наблюдаемого результата. Запустить именно его и записать ожидаемую причину падения. Отсутствующая зависимость, сломанный runner или синтаксическая ошибка не считаются доказательством нужного RED.
2. Если интерфейса ещё нет, добавить только тип/сигнатуру и минимальную заглушку, чтобы получить осмысленное падение проверки поведения. Не реализовывать функцию до первого такого падения.
3. **GREEN:** написать минимальную реализацию, достаточную для этого теста. Не добавлять следующий ресурс, экран или универсальный механизм «на будущее».
4. Добавить следующий граничный/ошибочный случай и снова пройти RED → GREEN. Не писать реализацию всей фазы между двумя запусками тестов.
5. **REFACTOR:** убрать дублирование и уточнить имена при зелёных тестах. Запустить затронутый набор и статические проверки. Публичный контракт менять вместе со всеми вызывающими местами.
6. Перед завершением задачи выполнить команды её выходного контроля и кратко зафиксировать результат.

Настройка Node, package scripts и первого runner — необходимый bootstrap до TDD. Не придумывать искусственно падающий тест «npm установлен». После запуска runner любая игровая логика и каждая локальная lint rule проходят RED → GREEN. Для графики автоматизировать геометрию/состояния/жизненный цикл; качество рисунка оценивать глазами по отдельному чеклисту.

Пример порядка для FEED:

```text
Тест: голодный живой кот получает сытость в допустимом диапазоне → RED.
Минимальная реализация FEED → GREEN.
Тест: значение не превышает 100 → RED → GREEN.
Тест: второе событие одного нажатия не кормит ещё раз → RED → GREEN.
Тест: мёртвого кота нельзя покормить → RED → GREEN.
Рефакторинг с сохранением зелёных проверок.
```

## 3. Контракты, которые нельзя переизобретать в каждой фазе

Ниже — целевые сигнатуры; вводить только необходимые текущей задаче поля. Типы и имена из архитектуры имеют приоритет. Отклонение фиксируется вместе с причиной, а не маскируется обходным импортом.

```ts
createRun(seed, runId): RunState
stepRun(run, stepMs, catalog): Transition
applyCommand(run, command, activeTimestamp, catalog): CommandTransition
selectGame(run, catalog): GameViewModel
selectCat(run): CatViewModel
selectHistory(save): HistoryViewModel
selectWorld(run, sceneDefinitions): WorldViewModel
decodeSave(raw: unknown): LoadResult
```

- `stepMs` — один фиксированный шаг 100 мс; внешний runtime разбивает допустимый elapsed на шаги. Нужды кота накапливаются до 5 секунд. Нельзя ускорять тест, передавая 30 минут одним неподдерживаемым шагом.
- `Transition` содержит новое состояние и небольшую коллекцию типизированных фактов/сигналов, необходимых приложению. Это возвращаемые значения, не глобальная шина событий.
- `CommandTransition` дополнительно содержит результат `applied | unavailable | unaffordable | cooldown`. Ожидаемый отказ не бросает исключение.
- `createGame` соединяет каталог, runtime, store и сохранение. Только публичный API `subscribe`/`dispatch` доступен UI. Snapshot глубоко read-only; нет публичных `setState`, `addMoney`, `killCat`, `unlockAll`.
- Часы и browser lifecycle внедряются на границе runtime. `game/` не знает о DOM, Svelte, Pixi, LocalStorage, `Date.now()` или `performance.now()`.
- Каталог получает типы из `game/`; симуляция принимает каталог аргументом. Нет циклических runtime-импортов между `game/` и `content/`.
- Pixi получает discovered-world projection и визуальные определения. Он не отправляет игровые команды. UI может отправить `acknowledgeUnlock` после показа, но эффекты открытия уже зафиксированы симуляцией.
- После окончания run симуляция заморожена. Историю и экран кота можно открывать; это не возобновляет нужды.

### Однозначная транзакция открытия технологии

Чтобы простой исполнитель не начислил один эффект дважды:

1. У upgrade есть условие появления текущего предложения, цена и максимальный уровень. Selector показывает только уже допустимое предложение; видимость не означает достаточность денег.
2. Для технологического перехода покупка сначала списывает цену и записывает upgrade level. `canDiscover` технологии проверяет покупку и prerequisites.
3. Новая технология один раз добавляет свои эффекты, History и pending announcement в той же транзакции. Первый эффект перехода принадлежит либо технологии, либо upgrade, но не обоим. В первых одноразовых переходах эффекты хранятся на технологии.
4. Для повторяемых upgrades их собственные эффекты рассчитываются по уровню без повторного открытия технологии.
5. Следующее предложение не появляется до acknowledgement предыдущего открытия. Пропуск/повтор acknowledgement не начисляет ничего.

В тесте обязательно проверять точную стоимость и однократность эффекта. Нельзя держать два независимых счётчика «настоящих» и «визуальных» unlocks.

## 4. Тестовые слои и данные

| Слой | Чем проверять | Что доказывает |
| --- | --- | --- |
| Чистые правила | Vitest, фиксированный seed, заданные входы | Команды, экономика, нужды, пороги, minigame, окончания |
| Runtime/store/storage | Vitest, fake monotonic clock, in-memory storage | Порядок обработки, пауза, подписки, ошибки записи |
| Custom lints | ESLint RuleTester/валидные и невалидные fixtures | Правило действительно отклоняет запрещённый код |
| Компоненты | Vitest + Svelte Testing Library там, где нужен DOM | Кнопки, роли, проекции, отсутствие скрытого содержимого |
| Браузер | Playwright, production preview | Реальная навигация, ввод, размеры, canvas и reload |
| Полное прохождение | Детерминированный headless scenario | Достижимость и временные границы при настоящей экономике |
| Устройство и арт | Ручной протокол iOS Safari/Android Chrome | Touch fairness, восприятие, GPU/память, пиксельная графика |

Файлы unit-тестов размещать рядом с модулем: `src/game/cat.test.ts`, `src/app/runtime.test.ts`. Проверки полного пути — `tests/scenarios/`; browser specs — `tests/browser/`; общие фабрики — `tests/helpers/`. Тесты исключить из чистого `tsconfig.game.json`; проверять их отдельной конфигурацией. Не ослаблять production-типы ради fixtures.

Правила данных:

- Для локального unit-теста можно создать небольшой явно заданный state около нужного порога. Фабрика обязана выдавать новый объект, без общей мутации между тестами.
- Тест целой концовки/полного пути начинается с `createRun`. Дальше — обычные команды, время и выборы. Прямое редактирование баланса, needs, unlock IDs или условий окончания запрещено.
- Сценарии не читают будущий каталог для выбора «лучшего» действия. Действуют по текущим offers/read models и явно описанной стратегии. Доступ к завершённому состоянию для проверки результата разрешён.
- Поздние browser fixtures можно получить из проверенного command-driven сценария и загрузить обычным путём сохранения. Это сокращение подготовки, не доказательство достижимости само по себе.
- Для старта не нужен property-testing framework. Табличные граничные случаи и несколько фиксированных seeds достаточны. Не сравнивать весь JSON state там, где требуется проверить один инвариант.
- Не мокать Pixi целиком ради «зелёного canvas». Геометрию тестировать отдельно, реальный рендер проверять браузером и вручную.
- Искусственно отправленный `visibilitychange` без изменения lifecycle-состояния документа не доказывает фоновую паузу. Инъекция lifecycle проверяет правила; реальное переключение приложений проверяется на телефоне.

## 5. Команды и выходной контроль

Команды вводятся в указанной фазе одновременно с первым реальным набором проверок. Не создавать скрипты с `passWithNoTests`, пустыми проверками или всегда успешными заглушками.

| Команда | Вводится | Назначение |
| --- | --- | --- |
| `npm ci`, `npm run dev`, `npm run build` | P00 | Воспроизводимая среда, разработка, production build |
| `npm run check:types`, `npm run lint`, `npm run format:check` | P00 | Статические гарантии |
| `npm run test:rules` | P00 | Fixtures линтеров |
| `npm run test:game -- <path>` | P01 | Vitest run для unit/integration/scenario без watch; имя сохраняется и для runtime/storage tests |
| `npm run check:content` | P02 | Валидность определений, затем manifest/scene metadata |
| `npm run test:browser -- <path>` | P03 | Playwright против собранного приложения |
| `npm run check:release-content` | P08 | Полный каталог, production-арт без placeholder и отсутствующих файлов |

`npm run check` объединяет существующие статические команды; при появлении `check:content` включает и её. Включать проверку в CI в той же задаче, где она стала настоящей. Prettier не переписывает весь репозиторий в feature-задаче. Размеры bundle сообщает production build или небольшой скрипт из P06.

**Задача завершена**, когда целевой тест прошёл после наблюдаемого RED, её регрессии зелёные, типы/линтеры проходят, production build не сломан. Проверки файлов документации не требуют запуска игрового набора. На границе фазы запускать все уже существующие тесты один раз. Повторять весь набор после каждого изменения текста не нужно.

Не менять ожидаемое поведение теста ради зелёного результата. Если баланс намеренно изменён, обновить именованные параметры и осмысленные временные ожидания в одной задаче; ограничения смерти, отсутствия offline-прогресса и независимости ухода не смягчать.

## 6. Рабочие решения для незаданных деталей

Это стартовые параметры, не новая продуктовая спецификация. Держать их в `content/balance.ts` и менять только вместе с обоснованием и затронутыми тестами:

| Параметр | Начальная величина |
| --- | --- |
| Первый ручной ввод | +1 output на принятое WRITE CODE |
| Первые покупки | Autocomplete: 10 output; snippets: 30; AI-native IDE: 90 |
| Первые эффекты | Autocomplete: +1 ручного output; snippets: +2 ручного output; IDE: +1 output/с и действие PROMPT |
| Токены/compute до агентов | Не видны, не требуются первыми покупками |
| PET | +3 mood сразу, затем cooldown 60 000 active ms |
| Еда | Целое 18–32; lock 1 000 active ms между принятыми FEED |
| Давление перекорма | При fullness ≥85 или overflow ≥10 добавить 25; иначе не добавлять; за приём не более одного добавления |
| Перекорм/болезнь | Пороги 40/80; спад 6/мин; болезнь добавляет потерю 1 mood/мин и 2 health/мин с нижним пределом 10 |
| Ускорение нужд действиями | +1% базового распада за осмысленное действие; максимум +10% за needs tick; после tick обнулить |
| PLAY | Ready 300 мс, движение 4 000 мс, result 300 мс; near miss — расстояние до края зоны ≤0,03 нормализованной длины |
| PLAY reward | Hit: seeded 8–12 mood; near miss: +1; miss: 0; 3 попытки, cap 100 |
| После фоновой паузы PLAY | Ready cue 500 мс без повторного счёта или нового target |
| Вмешательства кота | Mood 20–39: каждые 45 active s на 4 s; mood <20: каждые 25 s на 6 s; первое — после такого же интервала |
| Ограничение журнала | До 5 последних flavor-строк в UI, до 50 в памяти run; значимые History записи отдельно |

Остальные исходные needs/health rates — из архитектуры §6. Выздоровление +4 health/мин применяется только при fullness >35 и отсутствии болезни; при fullness ≤5 действует тяжёлый starvation rate вместо обычного. При противоречии стартовых параметров цели дизайна важнее: параметры подлежат настройке, инварианты — нет.

Для полного пути принять базовую тестовую стратегию: ручное действие раз в секунду в начале; после агента — не чаще раза в 5 секунд; покупать текущий progression offer при доступной цене; показывать и подтверждать открытия; обычное кормление раз в 180 секунд при fullness <70, PET раз в 60 секунд, PLAY раз в 270 секунд. Сессии PLAY расходуют реальное активное время сценария; их нельзя заменять прямой прибавкой mood. Скорость и точность ухода варьировать отдельными стратегиями в P11.

## 7. Передача результата следующему исполнителю

В начале реализации создать `docs/implementation_progress.md`; дальше изменять в нём только статус/факты. Не превращать сам план в журнал команд.

```text
Задача: P04.2
Статус: done / in_progress / blocked
Изменённые файлы: ...
RED: <тест> упал из-за <ожидаемое нарушение поведения>.
GREEN: <точные команды и результат>.
Рефакторинг: ... / не требовался.
Ограничения: ... / нет.
Следующая задача: P04.3
```

Фиксировать честно: отсутствие телефона означает незавершённую device-проверку, а не успешную приёмку. При блокировке не заменять Pixi/TypeScript/тесты фиктивными реализациями. Исправлять необходимую зависимость или записывать конкретную причину.

Шаблон задания простой модели:

```text
Выполни только Pxx.y из указанного файла фазы.
Прочитай docs/implementation_plan.md и связанные разделы архитектуры.
Сначала воспроизведи RED указанного поведения, затем реализуй минимум.
Сохрани границы модулей и посторонние изменения.
Запусти проверки задачи, обнови implementation_progress.md.
Сообщи реальные RED/GREEN и оставшиеся ограничения.
Не начинай следующую задачу до завершения текущей.
```

## 8. Настройки и музыкальная часть

По уточнению пользователя основной интерфейс включает **«Настройки → Звук»** и **«Настройки → Музыка → Music Lab»**, в том числе в production-сборке. Settings и Music submenu — панели внутри текущего игрового view; Lab — отдельный workbench entry с сохранением/паузой игры при переходе. Это не developer-only функция.

Задача P03.6 создаёт menu shell, [музыкальный TDD-план](sound_implementation_plan.md) реализует backend/Lab и подключение S07, P10.6 проверяет реальный production-путь. Ранний shell может явно показывать недоступный ещё звук; финальная приёмка не может подменить его просто меняющейся иконкой. Основной P10 теперь требует завершённый S07; тот опирается на основной P08 для полного mapping, не на P10, поэтому циклической зависимости нет.

## 9. Общий критерий завершения

Все обязательные задачи P00–P11 выполнены. Есть 28 технологий с различимыми иллюстрациями, полный автоматизированный путь около 30 активных минут, минимум 10 достижимых концовок, независимый живой кот с постоянной смертью и ровно три представления. Static checks, meaningful tests и production build зелёные. Отдельно приложены ручная мобильная приёмка, измерения загрузки/памяти/кадров и визуальная проверка. Семь дополнительных концовок отмечены как расширение и не подменяют обязательные десять.
